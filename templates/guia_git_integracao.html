Guia Git — Trabalho em Equipe e Integração

Este guia explica exatamente como o código produzido pelos grupos chegará ao projeto principal.

1. Por que não trabalhar todos na main?

A main representa a versão que deve estar estável. Se dez grupos alterarem diretamente a mesma branch, aumenta o risco de código incompleto, sobrescrita de alterações e conflitos difíceis de resolver.

Por isso vamos separar desenvolvimento e versão estável.

2. O que é uma branch?

Uma branch é uma linha independente de desenvolvimento dentro do mesmo repositório. Ela parte de um ponto existente do projeto e permite que uma equipe faça alterações sem modificar imediatamente a versão principal.

main
 │
 └── develop
      │
      ├── feature/grupo-01-manutencao
      ├── feature/grupo-02-combustivel
      ├── feature/grupo-03-ocorrencias
      └── feature/grupo-04-sla

Pense na branch como uma cópia controlada do caminho de desenvolvimento, conectada ao mesmo histórico do projeto.

3. O que é um commit?

É um registro no histórico dizendo: "neste ponto, estas alterações foram gravadas".

git add .
git commit -m "feat: adiciona controle de manutencao"

O primeiro comando prepara as alterações. O segundo grava essas alterações no histórico local.

4. O que é push?

É o envio dos commits da branch local para o GitHub.

git push -u origin feature/grupo-01-manutencao

Depois do push, o professor consegue visualizar a branch no repositório remoto.

5. O que é Pull Request?

É uma solicitação para incorporar o trabalho de uma branch em outra. No nosso projeto:

feature/grupo-01-manutencao
              ↓
          Pull Request
              ↓
           develop

O Pull Request permite revisar arquivos, discutir alterações, verificar testes e decidir quando a funcionalidade está pronta para integração.

6. Processo completo do grupo

  1. Atualizar develop.
  2. Criar a branch do grupo.
  3. Implementar somente o requisito recebido.
  4. Executar a aplicação.
  5. Testar a funcionalidade.
  6. Verificar git status.
  7. Adicionar os arquivos com git add.
  8. Criar um ou mais commits coerentes.
  9. Enviar a branch com git push.
  10. Abrir o Pull Request para develop.
  11. Aguardar revisão e correções, se necessárias.
  12. Após aprovação, realizar o merge.

7. E se houver conflito?

Conflito acontece quando o Git não consegue decidir automaticamente como combinar duas alterações. Isso é comum quando dois grupos alteram a mesma linha ou região do mesmo arquivo.

O procedimento será: identificar o arquivo, abrir os marcadores de conflito, comparar as versões, escolher ou combinar as soluções, testar novamente, criar um commit de resolução e atualizar o Pull Request.

<<<<<<< HEAD
versão atual
=======
versão da outra branch
>>>>>>> outra-branch

Não apague um bloco sem entender o que ele representa. Em caso de dúvida, pare e peça revisão.

8. Integração final

Depois que todos os grupos tiverem seus Pull Requests integrados em develop, faremos um teste integrado da aplicação inteira.

Somente depois da validação a versão de integração será promovida para main.

feature branches
      ↓
   Pull Requests
      ↓
    develop
      ↓
 teste integrado
      ↓
      main
      ↓
 versão estável
