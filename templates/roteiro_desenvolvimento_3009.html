🎯 Objetivo da prática

Você fará o trabalho como uma equipe de desenvolvimento de software. A aplicação LOGIEXPRESS já está funcionando. 1. Comece pelo projeto existente

O primeiro passo não é sair alterando o código. Antes de desenvolver, você precisa garantir que está trabalhando sobre a versão mais atual da develop.

Regra da prática: primeiro sincronize, depois crie sua branch e somente então comece a alterar os arquivos.
2. Sincronize a branch develop

Abra o terminal do Codespace e execute os comandos abaixo. Execute um comando por vez e observe o resultado. 

git fetch origin
git checkout develop
git pull origin develop
git fetch origin

Consulta o repositório remoto e atualiza as referências locais. Não altera seus arquivos de trabalho.

git checkout develop

Muda para a branch local develop.

git pull origin develop

Traz as alterações mais recentes de origin/develop para sua branch local.

Confira: se o Git informar que sua branch está atualizada, você pode continuar.
3. Crie sua branch de funcionalidade

Cada grupo deve possuir uma branch própria. O nome deve indicar claramente a funcionalidade que será desenvolvida.

Exemplo para o desafio Manutenção de veículos: 

git checkout -b feature/manutencao-veiculos

Outros exemplos: 

git checkout -b feature/controle-combustivel
git checkout -b feature/gestao-ocorrencias
git checkout -b feature/controle-sla
git checkout -b feature/controle-estoque
git checkout -b feature/timeline-entrega

Depois confirme em qual branch você está: 

git branch
A branch marcada com * deve ser a sua feature/....
4. Saiba exatamente quais arquivos podem ser alterados

🗂️ Mapa prático dos arquivos

Arquivo / pasta Quando alterar? O que normalmente entra aqui?
app.py Quase todas as novas funcionalidades Modelos SQLAlchemy, regras, consultas e rotas Flask.
templates/ Quando a funcionalidade precisa de telas HTML, formulários, tabelas, cards e Jinja2.
static/style.css Quando for necessário ajustar o visual Espaçamento, cards, tabelas, cores e responsividade.
templates/base.html Quando for necessário adicionar uma entrada ao menu Links de navegação do sistema.
tests/ Quando houver teste automatizado Testes das rotas e regras principais.
Atenção: não altere arquivos que não tenham relação com sua funcionalidade. Quanto menor e mais organizado for o conjunto de alterações, mais fácil será revisar e integrar o Pull Request.
5. Exemplo completo — Manutenção de veículos

O exemplo abaixo mostra a lógica de desenvolvimento. Ele não deve ser simplesmente copiado sem entendimento. A equipe deve adaptar os nomes, campos e regras à funcionalidade escolhida.

5.1 Criar o modelo no app.py

Uma manutenção precisa estar relacionada a um veículo. Um modelo simplificado poderia ser: 

class Manutencao(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    veiculo_id = db.Column(
        db.Integer,
        db.ForeignKey("veiculo.id"),
        nullable=False
    )
    data = db.Column(db.Date, nullable=False)
    tipo = db.Column(db.String(50), nullable=False)
    descricao = db.Column(db.String(255), nullable=False)
    custo = db.Column(db.Numeric(12, 2), nullable=False)
    status = db.Column(db.String(30), default="ABERTA")

    veiculo = db.relationship("Veiculo")
O que esse código representa? A classe representa uma tabela no banco. Cada atributo representa uma coluna. veiculo_id cria a relação entre a manutenção e o veículo.

5.2 Criar uma rota Flask 

@app.route("/manutencoes")
def manutencoes():
    registros = Manutencao.query.order_by(
        Manutencao.data.desc()
    ).all()

    return render_template(
        "manutencoes/list.html",
        registros=registros
    )

Essa rota consulta os dados e envia o resultado para uma página HTML.

5.4 Teste a navegação

Depois de criar a rota e o template, teste a aplicação no navegador. Se o endereço for /manutencoes, a rota precisa existir e o template precisa estar no caminho esperado.

Regra importante: antes de pensar em Git, faça a funcionalidade funcionar. Depois registre e publique o resultado.
6. Teste antes de fazer o commit

Execute a aplicação como você fez no dia 29/09: 

python app.py

Depois abra a aplicação pelo navegador e teste:

  • menu;
  • rota criada;
  • formulário;
  • cadastro;
  • edição;
  • exclusão, quando existir;
  • validações;
  • mensagens de erro e sucesso;
  • visualização em diferentes tamanhos de tela.

Se o projeto possuir testes automatizados para a funcionalidade, execute também: 

pytest -q
7. Veja exatamente o que foi alterado

Primeiro:

git status

O Git mostrará arquivos modificados, novos arquivos ou arquivos removidos.

Depois, veja as diferenças:

git diff

Quando estiver seguro de que as alterações pertencem à sua funcionalidade: 

git add .
Por que conferir? O comando git add . prepara todas as alterações do diretório. Por isso, git status e git diff são importantes para evitar enviar arquivos que não fazem parte do seu desafio.
8. Crie o commit

Registre a alteração com uma mensagem clara: 

git commit -m "Implementa manutenção de veículos"

Exemplos: 

git commit -m "Implementa controle de combustível"
git commit -m "Implementa gestão de ocorrências"
git commit -m "Implementa controle de SLA"
git commit -m "Implementa timeline de entrega"
Commit não é push. O commit registra a versão no histórico local do Git. O push publica essa versão no GitHub.
9. Publique sua branch no GitHub

Na primeira publicação da branch, utilize: 

git push -u origin feature/manutencao-veiculos

Depois disso, novos pushes dessa mesma branch podem ser feitos com: 

git push
Erro 403 / permission denied? Isso normalmente significa que sua conta não possui permissão de escrita no repositório do professor. Nesse caso, pare e informe o professor; não tente contornar a permissão.
O objetivo do push é publicar sua branch. A integração com develop acontece depois, por meio do Pull Request.
10. Pull Request → revisão → integração

10.1 Criar o Pull Request

Depois do git push, abra o GitHub e localize sua branch. Clique para criar um Pull Request.

O destino deve ser: 

base: develop
compare: feature/manutencao-veiculos

Título sugerido: 

Implementa manutenção de veículos

No corpo do Pull Request, explique:

  • qual problema foi resolvido;
  • qual funcionalidade foi criada;
  • quais arquivos foram alterados;
  • como a funcionalidade foi testada;
  • se existe algum ponto que precisa de atenção.

10.2 O que acontece depois?

O Pull Request será revisado. Se houver correções solicitadas, você volta para sua branch, altera o código, testa novamente, faz outro commit e executa: 

git add .
git commit -m "Corrige validação da manutenção"
git push

O mesmo Pull Request será atualizado automaticamente.

10.3 Integração

Depois da aprovação, o professor fará a integração da branch em develop. A branch main permanece reservada para a versão principal do produto.

Você concluiu o ciclo: branch → desenvolvimento → teste → commit → push → Pull Request → revisão → merge.
📋 Roteiro de comandos — copiar e colar

Para o grupo que está desenvolvendo a funcionalidade Manutenção de veículos, o roteiro completo é:

# 7. Verificar as alterações

# 8. Conferir as diferenças

# 9. Preparar as alterações
git add .

# 10. Criar o commit

# 11. Publicar a branch no GitHub
git push -u origin feature/manutencao-veiculos

# 12. Depois do push, abrir o Pull Request no GitHub
#    base: develop
#    compare: feature/manutencao-veiculos
Não execute tudo de uma vez. O bloco serve como roteiro. Os comandos de desenvolvimento, teste e Git devem ser executados em etapas, conferindo o resultado de cada uma.

⭐ Regras de ouro da prática
  1. Não desenvolva diretamente na main.
  2. Comece sempre pela develop atualizada.
  3. Cada grupo trabalha em sua própria branch.
  4. Teste antes de fazer commit.
  5. Confira o git status antes do git add.
  6. Use mensagens de commit que expliquem a alteração.
  7. O Pull Request deve apontar para develop.
  8. Correções solicitadas na revisão devem ser feitas na mesma branch.
  9. A integração em develop acontece somente depois da revisão.
  10. A main representa a versão principal do produto.
